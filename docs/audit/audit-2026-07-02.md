## [AXE 1/10] Architecture hexagonale + qualité code

**Niveau** : Fragile

**Justification** : le découpage domain / application / infrastructure est en place et
les domaines auth/categories/products sont propres, mais le domaine events cumule des
violations structurelles (port qui référence un DTO applicatif, adapter qui injecte une
classe concrète, modèle domaine sérialisé brut), et **aucun garde-fou automatique
(ArchUnit) n'empêche les régressions**.

**Findings 1a — hexagonal** :
- [MAJEUR] Le port domaine `EventService` importe les DTOs applicatifs `EventCreationRequest`/`EventUpdateRequest` — la couche domaine dépend de la couche application — `domain/ports/services/EventService.java:7-13`
- [MAJEUR] `EventRepositoryJpaImpl` injecte la classe concrète `ProductRepositoryJpaImpl` au lieu du port `ProductRepository` — `infrastructure/adapters/repositories/jpa/EventRepositoryJpaImpl.java:26`
- [MAJEUR] Les 5 mappers de la couche application importent les entités JPA d'infrastructure (`UserEntity`, `EventEntity`, `ProductEntity`, `CategoryEntity`, `PasswordResetTokenEntity`) — dépendance application → infrastructure ; le mapping domaine↔entité devrait vivre dans les adapters — `application/mappers/*.java`
- [MAJEUR] `Role` (modèle domaine) implémente `GrantedAuthority` de Spring Security — `domain/models/Role.java:3`
- [MAJEUR] `ProductRepository` (port domaine) porte l'annotation Spring `@Repository` — incohérent avec les 4 autres ports repository (sans annotation) — `domain/ports/repositories/ProductRepository.java:7`
- [MAJEUR] Aucun test ArchUnit ni règle automatisée d'architecture : toutes les violations ci-dessus sont passées inaperçues et rien n'empêche les suivantes — `backend/src/test/` (absent)
- [MINEUR] `EventServiceImpl.findEventById` fait `e.printStackTrace()` puis retourne `Optional.empty()` — erreurs masquées — `application/services/EventServiceImpl.java:145`
- [ASSUME] Résolution d'identité par `@CookieValue("jwt")` + `JwtService` dupliquée dans chaque controller au lieu de `SecurityContextHolder` — décision DEC-S1-003, migration actée en follow-up #93

**Findings 1b — REST** :
- [MAJEUR] `EventController` sérialise le **modèle domaine `Event` brut** en réponse (POST, PATCH) — aucun `EventResponse` DTO, contrairement à la règle AP-CAT-03 appliquée partout ailleurs — `EventController.java:46,71`
- [MINEUR] `POST /api/events` retourne 200 (`ResponseEntity.ok`) au lieu de 201 Created — `EventController.java:67` (le POST register et POST categories font correctement 201)
- [MINEUR] `AuthController` gère ses erreurs inline (try/catch + `ResponseEntity.status(...)` + corps String ad hoc) au lieu du `GlobalExceptionHandler` à corps JSON structuré — divergence de contrat d'erreur — `AuthController.java:96-250`
- [MINEUR] Nesting à 3 niveaux `GET /api/users/{userId}/products/{productId}/events` — limite recommandée : 2 — `ProductController.java:211`
- Nommage : pluriels corrects, pas de verbes dans les URLs (hors conventions auth `/login`, `/register`, `/me/change-password` — acceptées). Aucun finding.

**Findings 1c — DTOs & synchronisation front** :
- Inventaire : 17 DTOs backend (5 `*Response`, 12 `*Request`), 0 `*Dto` — nommage conforme. 0 DTO mort détecté (tous référencés par les controllers).
- [MAJEUR] Aucun pipeline de génération (OpenAPI → Zod) ni **test de parité** DTO↔schéma : la synchro est 100 % manuelle et a déjà produit deux désyncs actives (cf. axe 4 : BR-EVE-009 couleurs, BR-EVE-010 `allDay`/`isAllDay`) — `frontend/src/lib/schemas/`, `frontend/src/types/`
- [MINEUR] Les 17 DTOs sont des classes mutables (0 record Java) — `application/dtos/*.java`

**Recommandations priorisées** :
1. (P1) Introduire un `EventResponse` DTO + commande domaine pure dans le port `EventService` (supprime 2 MAJEUR d'un coup, débloque aussi BR-EVE-010).
2. (P1) Ajouter un test ArchUnit (3 règles : domain sans framework, domain/application sans infrastructure, adapters via ports) — verrouille l'existant.
3. (P2) Déplacer le mapping entité↔domaine dans les adapters JPA ; retirer `@Repository` du port et `GrantedAuthority` de `Role`.
4. (P2) Convertir les DTOs en records ; ajouter des tests de parité Zod↔DTO sur les 5 Response.

## [AXE 2/10] Sécurité OWASP

**Niveau** : Correct

**Justification** : défense en profondeur réelle et documentée — ownership vérifié sur
tous les verbes avec anti-énumération 404 (leçon PIT-S10-001 appliquée), cookie JWT
HttpOnly/Secure/SameSite=Lax, CSP par directives explicites, HSTS, rate-limiting keyé
`remoteAddr` (XFF opt-in), anti-énumération timing sur forgot-password (`@Async`),
`@Valid` sur 100 % des `@RequestBody`, secrets externalisés `${VAR}` avec profil prod
fail-fast et `ProfileSafetyGuard`. Aucun finding CRITIQUE applicatif. Les CVE de
dépendances sont portées par l'axe 8.

**Findings** :
- [MINEUR] Récurrence PIT-S7-003 non soldée : `authService.ts:61` + 3 composants (dashboard, EventContent, AddProducts — trackés #160) loggent encore l'objet axios `error` brut. Nota : `eventService.ts` (brut sur le commit audité 7ca36da) a été assaini par la PR #159 mergée sur dev le 2026-07-01 ; `apiClient.ts:111` logge un objet littéral restreint (url/method/response.data) — pattern déjà assaini, pas un finding
- [MINEUR] `JwtFilter` logge `warn "JWT Token not found"` sur **chaque** requête anonyme — bruit de logs exploitable pour du flooding, et signal utile noyé — `JwtFilter.java:56`
- [MINEUR] Incohérence de surface d'auth : `JwtFilter` accepte le fallback `Authorization: Bearer`, mais les controllers (`@CookieValue("jwt")`) ne lisent que le cookie → un client Bearer passe le filter chain puis reçoit 401 sur les endpoints à ownership — `JwtFilter.java:48-53` vs `CategoryController.java:51` et al.
- [MINEUR] `/api/auth/**` entier en `permitAll` + exclu du `JwtFilter` (`shouldNotFilter`), donc `/api/auth/me`, `/logout`, `/refresh` revalident le token manuellement dans le controller — correct aujourd'hui, mais chemin d'auth parallèle à maintenir — `SecurityConfig.java:127`, `JwtFilter.java:84-86`
- [ASSUME] CSRF désactivé + SameSite=Lax — DEC-S5-003, justification documentée (API JSON, cookie HttpOnly, CORS allowCredentials, pas de form-POST) + runbook `docs/runbook/cors-cookie-samesite.md`
- [ASSUME] Rate-limiting Bucket4j in-memory mono-instance (plafond effectif ×N derrière un LB) — DEC-S2-001, dette documentée
- [ASSUME] `BrevoEmailService` no-op silencieux si clé absente (risque prod : emails jamais envoyés sans alerte) — DEC-S8-001, follow-up fail-fast prod ouvert
- [ASSUME] Fallbacks dev committés (`jwt.secret` dev, `DB_PASSWORD` dev) dans `application-dev.properties` — DEC-S3-003 (profil prod sans default, fail-fast) ; aucun secret réel détecté par trivy

**Recommandations priorisées** :
1. (P1) Solder PIT-S7-003 : exécuter #160 en y ajoutant `authService.ts:61` (absent de son périmètre) + ajouter une règle ESLint (`no-console` ciblée ou règle custom) pour empêcher la récidive.
2. (P2) Exécuter le follow-up #93 (identité via `SecurityContextHolder`) — supprime le chemin d'auth parallèle et l'incohérence Bearer/cookie.
3. (P2) Passer le log « JWT Token not found » en `debug`.
