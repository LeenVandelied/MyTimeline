# Bugs résolus — MyTimeline

> Bugs notables corrigés, avec cause racine + fix. 4 lignes max par entrée.

## BUG-S4-001 — `/auth/refresh` : oracle d'énumération de compte (404 vs 401)
`refreshToken` renvoyait `404 "User not found"` quand le username d'un token signé valide n'existait pas en base, distinct du `401` token invalide → un attaquant énumère les comptes via tokens forgés (OWASP API3 / WSTG-IDNT-04). Fix : 401 avec body générique byte-identique au cas token expiré/invalide (`{"error":"token expiré ou invalide"}`), aucune ré-émission. (Sprint 4, review PR #113, commit 36772b4) — ⚠️ le même oracle subsiste sur `/me` (hors scope S4).

## BUG-S13-001 — `/api/auth/me` acceptait un token révoqué/déconnecté (révocation contournable)
`JwtFilter` bypasse `/api/auth/**` (BR-AUT-011) ; `AuthController.getUserDetails` validait signature+expiration mais PAS `isSessionActive(jti)` → un token révoqué (logout, DELETE session) lisait encore `/me` (200). Comme le frontend `AuthContext` déduit l'état d'auth de `/me`, la révocation de #73 était vidée de sa substance. Fix : `extractJti` + `isSessionActive` après `validateToken`, avant `ok()` → 401 si révoqué (commit fd91d9f). Clôt le « oracle subsiste sur /me » noté dans [[BUG-S4-001]]. (Sprint 13, review PR #176)

## BUG-S15-001 — POST /users/{id}/products sans `userId` au body → 400
`ProductCreationRequest.userId` est `@NotNull` et le `@RequestBody` a `@Valid` (`ProductController:50`) → la Bean Validation s'exécute AVANT `request.setUserId(path)` (ligne 68). Un body sans `userId` échoue en 400. Le front DOIT inclure `userId` dans le body (`productService.createProduct`) ; le backend le réécrit depuis le path (pas d'élévation de privilège). Vérifié contre le code (un finding review "dead code" était un FAUX positif). (Sprint 15 #163)

## BUG-S15-002 — `ProductDrawer` : événement couplé jamais envoyé (zodResolver strippe le champ)
`onSubmit` lisait `values.firstEventDate`, mais `zodResolver(schema.pick({name,category}))` STRIPPE les clés hors schéma des `values` passées à onSubmit → l'événement couplé n'était jamais envoyé (produit créé sans event, silencieux). Fix : `form.getValues('firstEventDate')` (état RHF brut, non filtré). Anti-pattern : lire dans onSubmit un champ absent du schéma resolver. (Sprint 15 #163)

## BUG-S27-001 — `SessionController` self-DoS : `revokeOtherSessions` via Bearer révoque TOUTES les sessions (jti cookie-only)
Après l'unification de l'identité en S27 #93 (`CallerResolver` accepte cookie OU Bearer), `SessionController` extrayait encore le `jti` COURANT du cookie SEUL. Client Bearer-only → `currentJti=null` → `SessionServiceImpl.revokeOtherSessions(userId, null)` → `revokeAllByUserIdExcept(userId, null)`, code path IDENTIQUE à `revokeAllSessions` → révoque toutes les sessions du user, y compris celle de l'appel (self-DoS ; `GET /api/sessions` : aucune session marquée « courante »). Détecté par `/review-pr 238` (security-expert indépendant), raté par la review intra-sprint. Fix (commit `e2580d1`) : helper `resolveToken(cookie, authHeader)` répliquant `JwtFilter` (cookie prioritaire, sinon `Bearer` substring(7)) sur `getActiveSessions` + `revokeOtherSessions` + garde `AnonymousAuthenticationToken` sur `CallerResolver` + 4 tests. Règle générale : [[PIT-S27-001]]. (Sprint 27 #93, review PR#238)

## BUG-S37-001 — `RateLimitingFilter` : body non borné + clé token non bornée sur endpoint public → OOM/DoS (corrigé avant merge)
En S37 (#141), l'ajout du throttle par-token sur `POST /api/auth/reset-password` (public, non authentifié) lisait le body entier sans borne et indexait `tokenBuckets` par le champ `token` brut (longueur non validée) → double vecteur OOM (gros body + clé Mo neutralisant le cap 100k). Détecté par convergence security-expert + reviewer au batch `/sprint start` PUIS reconfirmé en `/review-pr 282`, jamais mergé en l'état. Fix (`f7210e1`) : gate Content-Length 8 KiB + `readBounded(max+1)`, clé token plausible (≤128 chars) sinon repli IP, éviction LRU de `tokenBuckets`. Règle générale : [[PIT-S37-001]]. (Sprint 37 #141, reviews `/sprint start` + PR#282)

## BUG-S42-001 — Refacto de dé-duplication → écriture couleur en échec silencieux (rattrapé en review)
En S42 (`cd29644`, dé-duplication `EventContent` → `useEventEditConflict`), l'appel `await updateEventColor(...)` s'est retrouvé HORS try/catch dans `onSubmit`, avant `conflict.onSubmit` : sur échec, rejet non géré + `submitState` jamais posé → form figé sans feedback (régression du contrat #77). **Rattrapé par la re-review `/review-pr` (pas par la review batch mid-sprint).** Fix (`dbf12eb`) : appel supprimé (double-write redondant — le PATCH principal persiste déjà `color`). ## BUG-S42-002 — FreezingArchRule : nouveau getter sur entité boundary = nouvelle violation gelée
En S42, l'ajout de `EventEntity.getVersion()` appelé par `EventMapper.toDomain` (application→infra) crée une NOUVELLE violation ArchUnit gelée (le mapper est déjà une boundary connue). Symptôme : `ArchitectureTest` rouge tant que la ligne n'est pas ajoutée dans `backend/src/test/resources/archunit_store/<uuid>` (le matcher ignore les n° de ligne). Non-bloquant mais surprenant. À surveiller : la freeze-list mérite une revue mainteneur périodique (ne pas geler un contournement de règle plus large). (Sprint 42 absorb)

## BUG-S44-001 — `useFocusTrap` : `onEscape` en dépendance d'effet → callback instable = vol de focus pendant la saisie
En S44 (#300), `useFocusTrap(ref, active, onEscape)` (#63) liste `onEscape` dans les deps de son `useEffect`. Un appelant passant une lambda inline (`onClose={() => setOpen(false)}`) la recrée à CHAQUE rendu → l'effet se ré-exécute → re-trap → `first?.focus()` **ramène le focus sur le premier focusable pendant que l'utilisateur tape**. Symptôme trompeur : « le champ perd le focus à chaque frappe » (et tout rendu du parent — thème, pathname — suffit à déclencher). **Règle : tout callback passé à `useFocusTrap` (ou à un hook dont il est une dep d'effet) DOIT être stabilisé en `useCallback` chez l'appelant.** Appliqué : `AppShell.closeCreate = useCallback(..., [])`. (Sprint 44 #300)

## BUG-S45-001 — Garde serveur middleware : 500 sur 100 % des routes protégées, invisible en local
En S45 (#302), après le correctif sécurité « `Location` relatif », la garde renvoyait **500 au lieu de 307 sur toutes les routes protégées** (`/fr/dashboard` inclus), log serveur `TypeError: Invalid URL`. Passé au travers de `next build`, `tsc`, eslint et 33 tests unitaires de middleware, TOUS verts — les tests assertaient sur l'objet `NextResponse` et jamais sur le traitement de Next. **Détecté uniquement par le premier run CI e2e** (10/10 échecs `auth-guard.spec.ts` ; les 39 autres tests passaient, confinant la régression à #302). Diagnostic confirmé par reproduction runtime réelle (`next build` + `next start` → `ERR_INVALID_URL { input: '/fr/login' }`). Fix `2f5da3d` : `nextUrl.clone()` + `NextResponse.redirect(url, 307)`, vérifié en runtime sur toutes les routes (307 → `/fr/login`, 200 avec cookie). Test anti-régression **prouvé par revert** (8 FAIL). Règles : [[PIT-S45-001]], [[PAT-S45-003]]. (Sprint 45 #302, runs CI 30269383403 → 30273888611)

## BUG-S49-001 — `onScroll` synchronisait la minimap par `setState` à CHAQUE événement de scroll
En S49 (#69), la minimap de la frise était re-synchronisée par un `setState` sur **chaque** événement `scroll` → rendu complet de la frise par événement. **Mesuré comme le PREMIER poste de coût du scroll (frames p95 à 108 ms), devant le nombre de nœuds DOM** — autrement dit, la virtualisation seule n'aurait pas suffi. Corrigé par coalescence `requestAnimationFrame`. Enseignement : avant d'attaquer un problème de scroll par la réduction du DOM, mesurer d'abord le coût des `setState` déclenchés par le scroll lui-même. (Sprint 49 #69)

## BUG-S56-001 — En-tête de lane sticky : événements inatteignables à la souris, et l'issue sous-estimait la portée
En S56 (#392), `.mt-tlv__lane-label` (`position:sticky; left:0`, **opaque**) recouvrait en permanence les 168 px de tête du viewport de la frise ; le recouvrement ne diminue jamais au défilement, il part avec le viewport. `computeRange` (`padDays = 30`) pose le 1er événement à `30 × dayWidth` : **Trimestre = 150 px** et **Année = 66 px**, tous deux sous 168 → pastilles cliquables nulle part. **L'issue ne citait que « Trimestre » ; « Année » était cassé aussi, et plus fort** — trouvé en tabulant les 5 zooms plutôt qu'en vérifiant le cas cité. Aucun test unitaire ne pouvait le voir : jsdom ne fait pas de hit-testing (cf. `jsdom-scroll-tests-prove-nothing`). Prouvé par un E2E **rouge avant / vert après** avec oracle mesuré et `click()` **sans `force`** — c'est le hit-test de Playwright qui fait foi — sur fixture **stubbée** (sur le compte partagé, `rangeStart` dépend du minimum des dates de TOUS les événements du run : le test serait devenu vert à vide). Invariant de non-régression exprimé en repère rail, donc indépendant du scroll (`pillRailX >= headWidth`), vérifié aux **5** zooms. Effet de bord trouvé **à l'écran et non en test** : `buildRulerTicks` émet des graduations à offset négatif, jusque-là invisibles hors rail, que la gouttière faisait surgir en libellé flottant au-dessus de la colonne produit — masqué par un coin haut-gauche sticky. Correctif `143edc0`. Décision : [[DEC-S56-001]]. (Sprint 56 #392, PR #410)

## BUG-S59-001 — #341 : trois sprints de chasse à un SVG de landing qui n'existe pas
#341 décrivait « 4 `<g>` d'un SVG inline à x=384 pour un viewport de 375 px » sur la landing, observation issue d'une **mesure DOM, jamais d'une lecture du source**. Vérifié au S59 : aucun `<svg` ni `<g ` littéral dans `frontend/src/components/landing/*.tsx`, et **lucide-react 0.476 n'émet aucun `<g>`** (0 icône sur ~1500). Le coupable est le **bouton flottant des TanStack Query Devtools**, monté par `QueryProvider.tsx:40` sous `NODE_ENV === 'development'` — absent du bundle de production, décalé hors bord droit **par design**, son `right` suivant la largeur du viewport (329@320, **384@375**, 399@390 : correspondance exacte avec le chiffre de l'issue). **Il ne produit aucun scroll.** Mesure négative sur 20 combinaisons (4 locales × 5 largeurs), macOS **et** jammy : `scrollWidth == clientWidth` partout, `maxScrollX = 0`. Aucun correctif de rendu ; livré à la place un verrou E2E (`a62b3f7`) qui exclut l'outillage de dev et documente le piège. Règle : **une observation DOM issue d'un serveur de développement n'est pas une observation de l'application tant que l'outillage de dev n'a pas été exclu.** Cf. [[PIT-S59-002]]. (Sprint 59 #341)
